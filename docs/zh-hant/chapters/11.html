CHAPTER 11 / 14

題數、領域與執行預算

約 5 分鐘·資料快照 2026-09-21設計階段 Q0
先掌握這三件事
  • v0.3 完整任務庫目標改為 2,000–3,000 個正規化 G2；180 個藍圖是設計種子。
  • 先達任務規模與覆蓋門檻，再規劃例項、測例與執行量。
  • 原 100–140 情境只保留為舊版深入標註預算，不作全庫上限。
v0.3：主攻規模與覆蓋優勢

完整任務庫初始目標為 2,000–3,000 個正規化 G2，並要求至少最大可比基準 2 倍。180 個藍圖是設計種子；原 100–140 情境預算不再代表全庫規模。

1. 要達到什麼規模

專案 初始研發目標 正式驗收條件
完整模擬任務庫 2,000–3,000 個正規化 G2 任務定義 每個計入者都有可追蹤定義、相容例項、同介面專家解與經審核判分；此範圍目前是目標，不是取得／可行性估計
相對規模優勢 至少最大可比基準的 2 倍 在同一 ontology、task kind、scope、版本和去重規則下比較；參照最大值尚未完成正規化
人類觀測到執行 初始規劃 300–500 個 G2 任務，並接受相同的相對規模檢查 真的有人類觀測、合法目標配對與 robot 執行證據；不以合成 robot 影片代替人類資料
領域與能力廣度 對預先登記比較集合形成可驗證的覆蓋擴張 使用共同場域／家族／互動機制分類；公佈各基準已涵蓋、新增和未支援格子
統一入口 共用 registry、資料與任務查詢、執行介面規格、紀錄格式和報告 多 backend／profile 的適用集合可追蹤；不同輸入與 action contracts 分層比較

2,000–3,000 是這一輪的研發目標，沒有從目前原生紀錄數推匯出已完成的任務數。若對照庫正規化後比預期大，目標也要上調；若正式 release 沒達門檻，就公開實績並繼續擴張，不能先宣稱規模領先。

不設定「換成 20 個領域標籤就比較廣」這種門檻。原 12 個應用場域先保留為共同對映起點；新增場域必須有獨立的應用邊界、任務、場景與有效評測支援。共同分類若需擴充，必須同時重編對照工作。

7. 完整任務庫與深入模組的關係

完整模擬任務庫是規模主體。T1–T8 的資料與指標按各 task 的有效前提啟用，不預設所有任務同時支援全部模組。

原先 100–140 個情境的預算只保留為 v0.2 的深入標註成本示例；它不再是完整任務庫的規模目標，也不是 v0.3 的任務上限。人類觀測 track 另有 300–500 個 G2 的初始目標，並須對照最接近工作進行共同粒度審核。

影片題數、原始錄製 sessions、示範 pairs 和 robot trajectories 分開計數。只有模擬影片的專案不得標示為人類觀測任務；未收集的資料保持 0／TBD。

8. 任務規模確立後，再算評測量

以下只示範容量計算；每一項都需要有效、去重、相容：

2,000–3,000 個 G2 任務
× 每任務 10 個具體 G3 例項
= 20,000–30,000 個 task instances

× 每例項 2 種有效資訊條件 × 2 種介入條件
= 80,000–120,000 個 G4 case assignments

× 每個固定 case 3 次 policy repeats
= 240,000–360,000 次 planned rollouts／完整相容模型

8 個完整相容 baseline 系統
= 1,920,000–2,880,000 次主要 planned rollouts

實際數量以 eligibility、資料充分性、去重和方法覆蓋計算，不按乘法宣稱已完成。兩種資訊條件可能不等資訊，須作分層結果或診斷對照；兩種介入也可能對某些 task 不適用。

這些數量不含訓練、人類資料收集、oracle、額外消融、重複 training seeds 或人工審核。機器時數與人力須由 pilot 測得的單位成本估算；原 24 週排程不作 v0.3 的交付保證。

保留 14,400 的預算，需要明確定義配置

假設每個 blueprint 的所有配置與 bindings 都有效、彼此去重後不同，且選定 profile 全部相容：

120 blueprints × (3 seen + 3 unseen configurations) × 1 environment realization
= 720 scene-configuration assignments

720 × 2 goal bindings
= 1,440 task-instance assignments

1,440 × 2 intervention conditions
= 2,880 evaluation-case assignments

2,880 × 5 policy repeats on the same fixed cases
= 14,400 planned rollouts / compatible model

6–8 baseline systems
= 86,400–115,200 planned main rollouts

這些是 assignments 和容量預算，實際 unique G3／G4 必須依內容、有效性與去重確認。G2 不能從乘法匯出。

若「3 配置」指 seen／unseen 合計 3，則只有 1,440 case assignments、7,200 rollouts／模型；seen／unseen 是配置集合的屬性，不能在聯集算完後再乘 2。

若五個 seeds 改變初態，則保留同樣 14,400 次總執行時，可以變成 14,400 個 case assignments 各跑一次；這與 2,880 個固定 cases 各跑五次，對廣度和估計可靠度的意義不同。

Pilot 的現行計數

原設計的 16 個 pilot blueprints 來自 7 個場域標籤、13 個家族；其中 12 個剛體／程式、4 個布料。它是候選池。Milestone 建議 M1 後重選或分批，先集中 2–4 個實際場域，避免同時引入太多 backend／資料變因。

新版規劃示例為：16 blueprints×每 stratum 2 配置×2 strata×2 目標×2 介入×1 初態 realization＝256 case plans；再×5 policy repeats＝1,280 trial plans。舊檔案的「1,280 packets／episodes」在本報告統一為這種明確口徑；沒有任何實際執行。

QA 與影片數另算

舊版 8,640–14,400 只保留為原始標註工作量上界，不是去重 QA 數。來源活動、videos、clips、question schemas、unique input–target items、prompt variants、inference trials 要分開。

相同 clip 的同義改寫、介入前完全相同的畫面，或同一證據貼上互斥答案，都不能自動變成新的有效 semantic items。需先處理可回答性和 label 衝突。人類影片數、unique QA 數與預測 labels 目前都是 TBD，已收集實績為 0。

人力與計算成本

上述主執行量不含訓練、oracle、額外消融、重複訓練 runs、世界模型 labels 或新增機體。M2 應量到每 trial 的 wall-clock、reset、失敗重試、標註、人工驗收與儲存成本，再估正式預算。

主評測成本 ≈ Σ_method,case,repeat (模擬 + 模型推理 + reset + logging 成本)
總成本 = 主評測 + 訓練 + oracle/ablation + 資料/判分驗收 + 重現與發布

並行環境數不等於牆鐘時間必然等比例下降；五次重跑也不保證統計精度足夠。需要用 pilot 的實測 throughput 和群組相依性重估。
