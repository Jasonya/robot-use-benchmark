SCALE FIRST · v0.3

更多任务、更广覆盖，All-in-one。

完整任务库是论文主体。以共同粒度下的任务数与已验证覆盖作为规模主张，从完整来源库向 2,000–3,000 个 G2 推进。

2,000–3,000范式 G2 任务：初始研发目标
≥ 2×最大可比基准：相对验收门槛
5,020原生来源纪录：未完成跨作去重
0已验证测例／实际模拟运行

目前是规模优先的设计与来源盘点，尚未证明领先。2× 的分母要在共同 ontology、task kind、scope 和版本下范式；若对照规模更大，目标也上调。

探索完整来源纪录 →下载来源 CSV

更新：2026-09-22。研究主目标：以任务种类更多、涵盖更广、集成完整为主要贡献。

本版调整研究主线，不把原本 100–140 个情境的工程预算当作完整 benchmark 规模。原有 180 个情境保留为设计种子与验收范例。正式任务数使用共同范式后的 G2 定义，实际场景、测例与模型运行另外计数。

1. 要达到什么规模

项目 初始研发目标 正式验收条件
完整模拟任务库 2,000–3,000 个范式 G2 任务定义 每个计入者都有可追踪定义、兼容实例、同界面专家解与经审核判分；此范围目前是目标，不是取得／可行性估计
相对规模优势 至少最大可比基准的 2 倍 在同一 ontology、task kind、scope、版本和去重规则下比较；参照最大值尚未完成范式
人类观测到运行 初始规划 300–500 个 G2 任务，并接受相同的相对规模检查 真的有人类观测、合法目标配对与 robot 运行证据；不以合成 robot 视频代替人类数据
领域与能力广度 对预先登记比较集合形成可验证的覆盖扩张 使用共同场域／家族／交互机制分类；公布各基准已涵盖、添加和未支持格子
统一入口 共用 registry、数据与任务查找、运行界面规格、纪录格式和报告 多 backend／profile 的适用集合可追踪；不同输入与 action contracts 分层比较

2,000–3,000 是这一轮的研发目标，没有从目前原生纪录数推导出已完成的任务数。若对照库范式后比预期大，目标也要上调；若正式 release 没达门槛，就公开实绩并继续扩张，不能先宣称规模领先。

不设置「换成 20 个领域标签就比较广」这种门槛。原 12 个应用场域先保留为共同映射起点；添加场域必须有独立的应用边界、任务、场景与有效评测支持。共同分类若需扩充，必须同时重编对照工作。

2. 规模优势怎么证明

定义 T(w) 为工作 w 在共同规则下的范式任务集合，T(ours) 为本计划通过验收的集合。

TaskScaleRatio = |T(ours)| / max_w |T(w)|
初始验收目标：TaskScaleRatio ≥ 2

ReusedTasks = T(ours) ∩ union_w T(w)
NewTasks = T(ours) − union_w T(w)

这些集合目前尚未计算完成；NewTasks 不能由新 ID、文件名、自然语言改写或添加配置数得到。

领域广度另用预先固定的 context × family × interaction mechanism 格子及机体适用条件报告：

  • 对每个比较工作，列出共同覆盖、我们添加、我们仍缺少的格子。
  • 规模与广度主张都以通过验证的任务／格子为基础。
  • 不能只挑较小 benchmark 比较，或只取大型基准的 50 题子集来代表它的完整资源。
  • 比较 whole resource、正式 test subset、实际被每个模型运行的集合时，分开列数字。
  • 人类视频 QA、轨迹预测和 robot control 分开型态；不把不同型态的题相加作操作任务数。

3. 任务库从哪里来

采用完整来源库盘点，优先覆盖：

  1. 广泛活动与操作：BEHAVIOR-1K、RoboCasa、RLBench、LIBERO、Meta-World、ManiSkill、VLABench。
  2. 双臂、灵巧与柔性物：RoboTwin、SoftGym、DeformableRavens、GarmentLab、DexGarmentLab。
  3. 导航、对话与协作：ALFRED、TEACh、PARTNR，并保留其他导航／HRI 来源的扩展查核。
  4. 人类观测到运行：WatchAct、The Imitator Game、RoboReel 等；同时审核原始环境与示范来源。
  5. 集成型对照与基础设施：RoboVerse、Embodied Agent Interface、RoboDojo。既要比较，也可审核可复用组件。

上述来源的原生单位不同：活动目录、注册 ID、任务 class、schema、任务场景入口、示范程序、生成配置都要保留型态。原生纪录总和是盘点进度，不是独立 G2 任务数。

RoboVerse 等框架移植的 LIBERO／RLBench／ManiSkill 任务，不与原作简单重复相加。共享 simulator 也不等于任务语义完全相同；需要保留 environment dependency、task alias、版本变体和添加任务等不同来源关系。

具体来源、固定 commit、提取规则与所有原生纪录见本版附带的 inventory。来源表是可扩展清单，不宣称已穷尽所有既有工作。RoboReel 等尚未完成原生任务表提取的对照不得在 novelty 审核中被忽略。

4. 从原生纪录到真正的任务数

完整原生 task/config/scene inventory
→ 保留 native IDs、source versions、assets 与数据源
→ 处理同一来源的别名、版本与移植关系
→ 抽取 goal/reference/process/mechanism/validity 定义
→ 在共同规则下创建 G2 canonical task specs
→ 绑定 backend、profile、assets、初态与观测／动作约定
→ 同界面专家可解性与 reset 验证
→ 成功／近失败／合法替代的 evaluator 审核
→ 有效 G4 cases 与冻结 release

G2 的去重字段沿用 scale schema 1.0：task kind、typed goals、reference rules、goal/operator graph、必要过程、关键角色／机构／功能要求及有效结束语义。不能只靠标题 embedding 或相同终态 predicate 合并。

每个 spec 需要能回查「为什么与另一个相同或不同」。自动聚类只产生候选，对照规则和人工审核才决定正式数量。

5. 如何增加真正的任务种类

先计算已复用、去重且可验证的任务数 N_reused，再依覆盖缺口创建添加任务：

需要补足的规模 = max(0, N_target − N_reused)

添加候选可来自：

  • 原基准尚未覆盖、但人类程序数据中可辨识的完整工作目标。
  • 有实际用途的多步目标图、必要流程和资源依赖，而非任意排列步骤。
  • 关键机构、功能测试、材料交互或多人协作要求不同的任务。
  • 以历史、允许查找或版本化工作信息决定目标的不同指涉规则。

这些是产生候选的方法，不是已证明文献不存在的空白。每个候选仍要对照原任务联集、确认独立语义、创建实例与判分。

以下变化一般增加 G3／G4，不自动增加 G2：同义改写、颜色、对象身份、位置、相机、seed、机体更换、同一任务的额外视频。不同原作者可能把这些算作不同 native tasks，本计划必须一视同仁地重编。

6. All-in-one 的系统形式

全库使用一个 task ID／provenance／结果格式，但依真实能力需求分 backend 与兼容 track：

层 共同内容 各来源要绑定的内容
任务 G2 goals、必要流程、角色和成功语义 native task IDs 与对应证据
场景 instance、资产／物理／初态 hash 场景文件、reset、材料与几何
机体 profile、eligibility、observation/action contract robot、controller、控制频率与转换器
信息 text／human video／history／tools 的合法范围 来源配对、labels、时间、信息充分性
运行 reset／step／介入／trace 的共同记录 backend plugin 和原生有效性检查
评分 GoalSuccess、CompliantSuccess、coverage、uncertainty 原生 predicates、必要事件与校准容差

先审核并复用已有框架的 adapters／数据格式，不把「统一界面」本身宣称首次提出。RoboVerse 与 EAI 已有直接相关先例；本计划须以更大的已验证任务联集、覆盖及可重现实验证明扩充价值。

同一个 G2 在不同机体上实作仍只计一次语义任务；不同 profile 的可测集合、成功率和成本另列。每个模型实际跑了多少题，必须随结果一起公布。

7. 完整任务库与深入模块的关系

完整模拟任务库是规模主体。T1–T8 的数据与指针按各 task 的有效前提激活，不预设所有任务同时支持全部模块。

原先 100–140 个情境的预算只保留为 v0.2 的深入标注成本示例；它不再是完整任务库的规模目标，也不是 v0.3 的任务上限。人类观测 track 另有 300–500 个 G2 的初始目标，并须对照最接近工作进行共同粒度审核。

视频题数、原始录制 sessions、示范 pairs 和 robot trajectories 分开计数。只有模拟视频的项目不得标示为人类观测任务；未收集的数据保持 0／TBD。

8. 任务规模确立后，再算评测量

以下只示范容量计算；每一项都需要有效、去重、兼容：

2,000–3,000 个 G2 任务
× 每任务 10 个具体 G3 实例
= 20,000–30,000 个 task instances

× 每实例 2 种有效信息条件 × 2 种介入条件
= 80,000–120,000 个 G4 case assignments

× 每个固定 case 3 次 policy repeats
= 240,000–360,000 次 planned rollouts／完整兼容模型

8 个完整兼容 baseline 系统
= 1,920,000–2,880,000 次主要 planned rollouts

实际数量以 eligibility、数据充分性、去重和方法覆盖计算，不按乘法宣称已完成。两种信息条件可能不等信息，须作分层结果或诊断对照；两种介入也可能对某些 task 不适用。

这些数量不含训练、人类数据收集、oracle、额外消融、重复 training seeds 或人工审核。机器时数与人力须由 pilot 测得的单位成本估算；原 24 周调度不作 v0.3 的交付保证。

9. Milestones 改成规模与有效性的验收阶梯

阶段 交付 通过条件
S0 完整来源盘点 官方来源、固定版本、完整 native IDs、型态与 lineage 提取规则可重跑；混合单位与来源重复不被隐藏
S1 共同比较与去重 baseline task sets、G2 mapping、分歧审核、覆盖矩阵 能确定最大可比基准及本版增量；正式目标依结果调整
S2 跨 backend 最小闭环 代表性刚体、机构、布料、移动／协作 anchors 初始 6–8 个 anchors 只验证界面与判分，不作论文规模上限
S3 批量扩展到 250／500／1,000 每批已绑定、可解、可评分的 G2 与实例 每批同时通过品质与来源检查，公布实际成功移植率与成本
S4 规模门槛 朝 2,000–3,000 个 G2 推进，完成 relative-size 与 coverage checks 达共同口径的 2× 门槛，或据实记录尚未达成并继续扩展

10. 论文的主比较表

主表同时列：

  1. 原作者 native counts 与共同范式 G2 counts。
  2. 完整资源库、可取得部分、已实例化部分、正式评测 subset。
  3. 领域／家族／交互机制覆盖，以及同一 G2 在多机体实作的情况。
  4. inherited、modified、genuinely new specs 的来源与判定规则。
  5. human-observation-conditioned tasks 的实际数量与配对品质。
  6. G3、typed G4、G5 和数据资源量。

主实验应包括全库与各来源／领域的 macro 结果、held-out 语义／对象／材料条件、规模增加后的排序稳定性、以及视频／过程／恢复诊断。不能用大量相似取放样本掩盖其他机制的弱项。

11. 目前已完成与仍未完成

本次完成的是规模主线重设、官方来源版本盘点、可追溯原生纪录提取与网站规划更新。静态来源纪录可作为构建大型任务库的输入。

目前仍没有共同范式后的完整 G2 计数、实际 instance、已验证 cases 或 simulator rollouts。因此本版不宣称已建成最大 benchmark，也不把来源库条目自动登记为本计划完成的任务。

本版的承诺是把规模与覆盖优势作为主要验收目标，并沿完整任务库路线推进。

3. 会改变规模比较的查核结果

RoboCasa：完整任务目录与有数据的子集不同。 固定版本的官方 task catalogue 有 365 个名称，dataset registry 只有 317 个对应名称。此次保留全部 365，另外记录是否出现在 dataset registry，避免把数据子集误当完整 benchmark。

RoboVerse：注册名不等于独立任务。 本次读到 2,897 组 literal task registrations；同一注册调用的别名保存在同一纪录。两个 ManiSkill 集成文件合计 2,589 组，其中 2,587 个衍生 class 只赋值 scenario 和／或 traj_filepath、没有自己的方法覆写；另有 2 个基类。这是可查核的配置展开现象，不是整个 RoboVerse 被正式归一成两个任务。

这两个文件的基类还明示了与原 ManiSkill checker 或几何设置的差异。因此，跨框架的 task 名相似也不能直接声明完整语义等价。

WatchAct：14 个原生『tasks』是认知评测 schema。 官方表包含 imitation、reversal、count、state change 等类型。不能直接把它们视为 14 个唯一的机器人操作 G2；完整物理任务数需连外部 JSONL／BDDL 与目标定义一起审核。

The Imitator Game：保留 base mapping 与 levels。 此次提取 53 个人类／模拟任务映射，L0–L3 和其他原生 IDs 保留为对应字段，没有将每个 level 都自动多算一个 base task。

旧 repo／版本要另外确认。 旧 BDDL URL 会导向 100 活动版本；BEHAVIOR-1K 应读目前官方 monorepo 的 bddl3 subtree。ManiSkill2 的旧 repo 是转址指引，实际较早 task bank 改由官方保留的 v0.5.3 commit 盘点。

4. 已完成与未完成

  • 已完成：固定版本、树未截断检查、原生 ID／class／schema 提取、别名保留、部分来源关系、型态分列及计数一致性验证。
  • 尚未完成：全库 G2 范式、跨来源语义去重、资产下载、实例化、专家可解性、evaluator 与模型实验。
  • 所有正式 instance／case／rollout 数仍为 0；正式 G2 数为 TBD。

5. 下一步如何服务规模目标

以这份可追溯盘点作为 2,000–3,000 个 G2 研发目标的输入。先确定去重、可复用且可验证的任务联集，再用新目标结构、必要流程与交互机制补足缺口。不能用这里的 5,020 直接宣称已超过既有 benchmark。

每个比较工作要同时保留原生计数、范式任务数、可取得资产范围和实际评测集合。集成框架不可被忽略，也不可与它引入的上游任务重复加总。

6. 文件与重建

  • native_source_inventory.csv/json：所有原生纪录、固定来源、型态、别名与证据界线。
  • source_extraction_report.json：各来源的提取规则、计数与未解决问题。
  • pinned_sources.json：官方 repo、commit、原生来源范围。
  • source_catalogue.json、fetch_sources.py、extract_inventory.py：可重建的来源盘点入口。

原始程序仅存于本机研究 cache，不放入网站输出；公开输出主要是 task IDs、路径、来源链、metadata 与本计划的分析。
