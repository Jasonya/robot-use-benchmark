OVERALL DESIGN · v0.4

任务多、涵盖广，放进同一套评测。

整个 benchmark 改成大型任务库、具体广度配额与共用评测平台。每批扩张都同时检查「多了哪些任务」和「补足哪些覆盖」。

2026-09-22研发目标提案 · 尚未达成模拟环境
先掌握这三件事
  • 全库初始目标 2,000–3,000 种独立任务；任务数与有效覆盖各以至少最大可比基准 2 倍为目标。
  • 12 个核心场域各提出 100 个有效任务绑定、8 个家族、3 类机制的最低支撑量。
  • 同一任务换场域或机体，增加覆盖、实例和实作量；全球 G2 只计一次。
  1. 01完整来源库原作、版本、原生 ID 与来源关系
  2. 02独立任务库合并重复、保留真正不同的目标与流程
  3. 03广度与实例跨场域、材料、机体创建有效情境
  4. 04统一评测平台共用入口、合法测例、判分与结果
看目标与共同门槛 ↓查前作规模与来源 →

更新：2026-09-22。研究范围仍是模拟。这是一份整体研发设计，没有把尚未实作的任务、场景或实验列为成果。

整个设计改成：完整来源任务库 → 范式任务库 → 广度约束下的场景实例 → 共用评测平台。

主目标同时要求「真正不同的任务多」、「实际覆盖的场域与机制广」和「一套入口能管理与评测」。2,000–3,000 个范式任务仍是初始研发目标；数量和覆盖要各自验收。

领域广度 有 12 个场域标签与候选矩阵 每个场域须有足量、跨家族与机制的可解任务；与基准使用同一分类

2. 用四层数据把整套系统串起来

层 内容 数量代表什么
来源层 原作、commit、native task ID、class、schema、资产引用、数据 lineage 目前 5,020 笔原生纪录；不同型态不能直接当独立任务
任务层 全球唯一 task spec ID、目标、指涉规则、必要流程、功能／机制与成功语义 范式 G2；本版初始目标 2,000–3,000
实例层 task 绑定应用场域、backend、机体、真实资产、材料与可追踪初态 G3；同一 G2 可在多个场域或机体创建实例
评测层 instance 加输入、历史、介入、预算、labels、判分器，再交给模型运行 typed G4 cases 与 G5 trials；与任务种类分开

例如「折好并收纳指定布品」是一个任务定义，可以在住家和旅宿各创建有效情境，也可在不同双臂机体上实作。全库的语义任务只计一次；添加的是 task–context 或 execution bindings、实例和覆盖。

→ 全球 task spec 与来源对应
→ task × context 的有效绑定
→ task × context × profile × backend contract 的运行绑定
→ 实际资产／初态
→ 各模块的合法测例
→ policy 运行
→ 结果、trace、覆盖与统计

3. 「大」和「广」设成两道共同门槛

以下数字是本计划的研发验收提案，不是文献公认标准或已完成的结果。在 S1 完成共同分类、参照集与可行性分析后，确认并预先登记；之后若变更要升版本并解释原因，不能看完 test 结果才改口径。

验收项目 v0.4 提案
全球独立任务数 初始目标 2,000–3,000 个 G2；每个计入者都有有效实例、专家解与判分器审核
相对规模 至少最大可比基准的 2 倍 G2，分母须以同一 task kind、scope、版本与范式规则取得
相对广度 至少最大可比基准的 2 倍有效 coverage cells；格子定义见下文
内核场域 起始 12 个共同场域均需要实际覆盖；若参照集或新任务涉及其他应用，先扩充共同 ontology 再比较
每个核心场域 至少 100 个不同 G2 的有效 task–context 绑定、8 个任务家族、3 类交互／流程机制
有效覆盖格子 至少由 1 个 G2、3 个不同且有效的 G3 初态／实例，以及专家与判分证据支持
非刚体材料 布料、绳索、颗粒、流体、柔顺固体各初步要求至少 20 个适用 G2、3 个家族；实际模型与量测必须有效
机体广度 至少固定单臂、双臂／灵巧、移动操作三组运行 track，各有至少 100 个适用 G2；全身／人形继续扩展
人类观测 track 初始目标 300–500 个 G2，至少 8 个共同应用场域；来源视角、剪辑方式与实际配对量另报

2,000–3,000 是初始规划区间，不是硬性上限。若最大可比基准的共同 G2 数量超过 1,500，至少 2× 的目标就需要超过 3,000；先按共同规则完成比较，再上调建置目标。

每个场域的 100 个 G2 可以与其他场域重叠；每个机体的 G2 也可能重叠。这些是广度支撑要求，不能相加成全库任务数。机体 track 也不是增加 G2 的理由。

coverage cell 定义为：

共同应用场域 D × 主要任务家族 F × 任务真正需要的交互／流程机制 K

一格必须能回查实际 task/context/instance IDs、有效 reset、可解性和判分证据。相机视角、可额外产生的问答、任意能力标签或 profile 数不能直接乘进格子数。

同一 G3 可能支持数个真正需要的机制；这些是非互斥覆盖，仍要保留支撑证据。没有足够实例支持的格子列为薄弱／待验证，不提前计入主张。

与前作比较的共同规则

规模与广度各自取比较集合中的最大值，可能来自不同工作。比较集合在 S1 冻结，包含大型任务库、专门机制库和集成框架；原作的完整资源与正式实验 subset 分栏。

每项证据区分「原作报告」「公开定义可映射」「有同等实例／专家／判分支持」和「本计划重跑验证」。对前作与我们使用同一计入规则；公开数据不足填 unknown，不能当成 0 来拉高倍数。若最大分母仍未知，只报已核对范围、缺失比例和界限，不宣布 2× 已达成。

同时公布相对每个前作、相对前作联集的共有／添加／缺失格子，以及 F/K 较粗、主要和较细粒度的敏感性分析。只用一套有利于自己的分类得到 2×，不足以支持稳健的广度优势。场域、家族、机制的边际数量与实际分布也一起报告，不能只留一个总分。

4. 广度如何落到任务分配

内核场域 应包含的完整工作方向 特别需要避免的薄弱覆盖
D01 居家生活 整理、取物、布品处理、设备程序、复原 只有桌面取放
D02 餐饮服务 备料程序、摆设、配送、回收、物料处理 只换不同食物名称
D03 零售门店 拣选、陈列、盘点、包装、补货 只有商品辨识
D04 仓储配送 订单集货、装箱、载荷搬运、多站服务 只有导航到点
D05 办公行政 文件与物品管理、设备流程、信息到实体工作 只有数字问答
D06 工坊制造维修 工具、插接、拆装、紧固、功能验收 只碰触零件、不验功能
D07 实验室例行对象操作 惰性物品、容器、配量、设备与纪录流程 宣称未模拟的化学／生物效果
D08 旅宿洗衣 分类、展开、折叠、悬挂、收纳、周转 只有单一折毛巾设置
D09 设施维护 耗材更换、表面处理、设备复位、工具管理 接触覆盖被当成实际消毒
D10 园艺户外 工具、容器、材料、支承、搬运与户外配置 用植物外观代替生长或作业效果
D11 非临床辅助生活 意图相关取物、交接、等待、协助与协作 将模拟 partner 结果当真实人类体验
D12 公共场馆活动 场地准备、对象整理、服务、共享资源、复原 换场馆名称但任务与条件不变

这 12 类是已有分类的起点，不能靠拆细名称制造广度。来源任务若落在真正不同的新应用范围，就扩充 ontology，并用同一版本重新映射所有比较工作。

场域绑定要有任务相关的环境、流程、资源或角色条件。只有改背景图、房间名称或用途标签，不算添加的有效场域覆盖。

分布控制

完整任务库保留所有合格任务，不为了表面均衡而删除大量已复用任务。任务库的实际分布、跨场域重叠和来源集中度都公开。

正式结果同时提供：

  • 场域等权 macro 结果：每个核心场域权重相同，再在场域内按预先定义的家族／任务权重聚合。
  • 完整任务库 micro 结果：保留真实样本分布，和 macro 分开呈现。
  • 每个场域／家族／材料的覆盖与成功率：缺项和薄弱项可见。

这避免把「单一场域占比上限」错套成任务库删题规则，也避免大量居家／厨房样本直接决定整体排名。每个方法实际接受的 eligible 集合先冻结，不能自行只挑擅长的题。

5. 材料、机体与观测各自管理

材料与机制

六种物理材料模型仍分开：刚体、布料、绳索、颗粒、流体、其他柔顺固体。关节、扣件、容器与多零件结构另记，不当成材料。

交互／流程机制先提出九组共同索引，待 S1 与原生任务共同审核：

ID 机制 需要的证据
K01 抓取、放置与支承 对象身份、接触、位置和稳定性
K02 关节、封口与设备状态 机构状态、必要事件、合法转移
K03 精密接触、插接、紧固与功能装配 配合／连接状态、工具作用与功能结果
K04 形变、层次、拓扑与柔性结构 材料状态、形状／边／拓扑与稳定释放
K05 物料转移、配量与可验证混合 量、残量、流失与模型有效性
K06 工具作用、表面处理与非抓取操作 任务相关接触或作用结果
K07 导航、载荷与移动操作 到达、载荷保持、交付与路径事件
K08 交接、共同支承、时序与角色协作 partner 协定、共同结果与干扰
K09 由历史或数字查找决定实体目标 合法信息、身份／版本指涉与实体结果

K 是交互／流程索引；不是九种材料，也不取代原有 C01–C34 能力标签或 T1–T8 模块。只有任务真正需要且有证据的机制才参与 coverage 计数。

纯设备状态机可支持程序评测，但不冒充热学、化学、清洗或其他未模拟的物理效果。材料覆盖需由对应模型、量测与有效性检查支持。

机体

保留六个候选 profile，先创建三组明确可运行 track：

  • 固定单臂：以 R1 为起点。
  • 双臂／灵巧操作：以 R2／R3 为起点，依不同控制与手部界面分层。
  • 移动操作：以 R4／R5 为起点，底座与手臂的控制约定固定。

R6 全身／人形可以继续扩展。每个被宣称支持的 profile 都须有真实 adapter、可解性与结果；不能只靠 ontology 中有这个名称就算覆盖。

观测

保留文字、头戴、胸前／身体、外部／多视角、VLOG／剪辑、robot 示范、多 session 历史等来源。相机安装、agent origin、剪辑、语言、history 与 sensors 分栏记录。

人类观测 track 必须真的有人的观测与合法 goal pairing，不能以 robot 模拟视频补数。没有校准的视频仍可作语义测试，但不宣称有度量 3D 标签。

6. 任务怎么建出来

任务来源分为三类：

  1. 直接复用：原生任务、初态、控制与判分对得上，通过同界面验证。
  2. 移植或修改：保留来源与改动清单，重新检查 simulator、assets、controller、目标与判分。
  3. 补足新任务：针对广度矩阵的真实缺口，创建新目标、必要流程或交互机制，再对照已有任务联集确认增量。

添加候选可以取材自人类程序与活动文献、具体部署工作流、既有资产的合理重组。但只改名称、颜色、位置、相机、seed 或不必要的步骤，不能自动增加 G2。

每个 G2 必须保存完整的合并／拆分理由。共同规则先固定，对我们与对照工作一致套用；抽样隐去来源做独立覆核，避免为了让数字好看而采不同粒度。

一个完整工作也不应只因有多个控制动作就多算多个任务。主要 task bank 收录有独立用户目标与完整 outcome 的规格；仅作控制校准或子技能诊断的项目另列。原生、短组合与完整工作流的分布仍须分开报告。

7. 平台架构改成可替换的模块

同一个研究／评测入口
    ↓
Task Registry + Source/Dedup Ledger
    ↓
Task–Context / Execution Binding Builder
    ↓
Observation & Dataset Builder
    ↓
Simulator Adapter ↔ Policy Adapter
    ↓
Evaluator + Event/Trace Recorder
    ↓
Coverage / Statistics / Result Package
    ↓
网站、下载与核验排行榜

Task Registry 是共同内核。Backend 可以不同，但每次运行必须固定 robot、action、观测、数据、时间与介入条件。

每个 backend adapter 至少要提供 reset、step、允许观测、evaluator 私有状态、介入、snapshot 和 trace。Policy adapter 负责不同模型的输入与动作约定。共同格式不表示跨引擎动力学或 action space 相同。

可以审核复用 RoboVerse、EAI 及各原生环境的界面与组件，但需要保留原作的角色与限制。真正的增量要由任务库、覆盖与可重现结果证明。

网站已能公开阅读与搜索，正式运行服务尚未实作。未来采下载自行运行或平台代跑，皆使用同一 release／case／trace 格式；核验状态明确区分。

8. 评测内核保留，改成全库与模块分层

T5 完整运行与 T6 恢复是机器人使用能力的主体。 T1 理解、T2 记忆、T3 预测、T4 规划、T7 协作、T8 世界模型连到同一 task／instance，在数据足够时产生合法 packets。

不是每个任务都自动有八种测例。每个模块报告自己的适用 G2、instance、数据源与有效测例数。

主结果保留：

  • GoalSuccess 与 CompliantSuccess，分别看终态与完整明订要求。
  • 成对目标成功与视频／文字／单帧／无视频对照；信息不等量时清楚解读。
  • 完整 episode 成功、介入施加率与条件式恢复；snapshot replanning 另报。
  • 时间、动作、允许询问、禁止介入与副作用。
  • oracle goal／state／plan 的瓶颈诊断。
  • 按 task family、场域、机制、材料、profile 与条件的 macro 分布及不确定性。

完整 task bank 的正式 T5 评测不能只跑原 100–140 个案例，却宣称全部 2,000 个都经过比较。每个方法／track 都公布完整 eligible G2 与实际运行集合；昂贵的视频或专门诊断子集另外报告。

数据仍先按来源活动／录制 session／资产家族切分，再生成 clips、QA、plans 或其他衍生标签。冻结、脱机适应、few-shot、online 和 continual learning 分开；公开预训练未知的情况如实记录。

难度先保留十维设计描述，再以固定 agent panel 和 contract 校准。场景多、步骤多或视频长本身不等于经验难度。

难度如何在大题库中量化

先替测例记录任务链、精度、遮挡、形变、记忆等设计条件，用它们检查分布和抽样。这些描述不直接决定「难／易」。

正式难度以同一评测模块、输入／控制约定和固定方法群下的成功率估计：

D_empirical(case, contract) = 100 × (1 − 加权平均成功率)

方法权重、重复次数和不确定性估计先固定；共享 checkpoint 的方法不当成大量独立证据。任务层只在预先定义的 instance 分布上聚合。可依冻结的校准集划分四个难度区间，实际边界由 S3 pilot 校准并在 S5 前冻结；目前不替 5,020 笔来源纪录虚填难度级别。

全方法失败先检查专家解、reset、信息充分性和判分器，再判定是否高难度。难度、评测鉴别力和任务的重要性各自报告；换方法群或 control contract 后，要重新检查量尺。

9. 同时做大和做广后，预算怎么算

添加场域和机体会增加实作与测试量，但不必增加 G2。因此 v0.4 明确分三种集合：

N_task = 全球唯一的 G2 task specs
B_context = 不同 (task, context) 有效绑定
B_execution = 不同 (task, context, profile, backend contract) 运行绑定

一个纯规划示例：

层级 假设 规划数量
G2 全球去重任务 2,400
Task–context bindings 部分任务在多场域使用 2,800
Execution bindings 部分场域再支持另一机体／contract 3,000
G3 assignments 每运行绑定 10 个不同有效初态 30,000
G4 assignments 每实例 2 种有效信息条件 × 2 种介入 120,000
G5／完整兼容模型 每固定 case 3 次 policy repeats 360,000
8 个完整兼容方法 主运行量，不含训练和额外消融 2,880,000

这个例子仍只有 2,400 个 G2 任务，不能因为有 2,800 个场域绑定或 3,000 个运行绑定而改报成更多任务。

各模型未必适用全体 bindings，信息与介入也不一定每题都适用。实际预算应对合法 eligible records 加总，不把乘法当已去重的实绩。单位时间、人力与计算成本由 pilot 量测，没有假设既有 24 周示例可以直接交付全量。

10. Milestones 重新对齐整体目标

阶段 主要交付 验收重点
S0 来源盘点 完整 native records、版本、单位与 lineage 本轮已有 5,020 笔静态纪录；不算成正式任务数
S1 共同分类与缺口 G2 规则、参照集、F/K 分类、场域矩阵与配额定版 确定两个相对门槛的分母；不能只挑较小对照
S2 跨 backend 闭环 代表性 6–8 个 anchors、实例、专家解与判分 验证界面和量测；不是论文规模上限
S3 批量扩张 250／500／1,000 个验证任务及其 bindings 每批同时看 N_task 和各广度配额，避免只扩容易的一类
S4 达双门槛 向 2,000–3,000 与更多有效覆盖推进 任务规模及 coverage ratio 同时达标，内核场域／材料／机体支撑足够
S5 冻结与主实验 固定测例、完整 eligible 集合、基线、oracle／ablation 所有正式结果能回查版本、cases 和 traces；测试后不挑题
S6 发布与论文 code、data、evaluator、核验结果与完整稿件 「更多、更广、统一」每个主张都有相应证据

设计网站和阶段性 beta 可以持续公开；只有通过共同门槛的正式版本，才能标示已达成「规模与广度优势」。未达时公开进度并继续扩充，不以换单位或降标准代替成果。

11. 论文最后要怎么呈现

主表同时列出：native counts、范式 G2、有效场域／家族／机制格子、材料与机体支撑、G3、typed G4、实际 G5，以及数据源量。

与对照工作的完整资源、可取得部分、已实例化部分和实验 subset 分栏。原生 task、数据 episodes、视频 QA 和 benchmark wrappers 不能直接混加。

论文的主实验须回答：扩大的任务库与覆盖是否带来稳定、可解释的新评测证据；哪些领域、材料、流程与来源仍是瓶颈；添加任务相对原作联集有何真正差异。统一界面本身已有相关工作，不单独当作新颖性。

12. 目前进度与下一个具体产物

目前已完成研究文件、网站、规模主线、来源盘点与本版整体设计。既有 5,020 笔静态纪录来自 20 个官方程式库、21 个版本来源；它们仍未完成共同 G2 去重。

目前 G2 正式总数为 TBD，已实例化任务、已验证测例、实际模拟运行和本计划收集的人类视频 pairs 均为 0。

下一个具体产物是 G2／task–context／机制的审核表及缺口清单：每列连回原定义，记录合并／拆分理由、资产与界面需求、可行性，以及它补足哪个广度格子。依这份表安排实作批量，并同步审核可用 backend 与 profile。

交互估算：做广之后，需要跑多少？

纯规划示例：固定 2,400 种独立任务、2,800 个场域绑定、3,000 个运行绑定。调整下列条件，独立任务数仍是 2,400。

30,000G3 实例配置
120,000G4 合法测例配置
360,000每个方法的运行量
2,880,000所有方法的总运行量

4 种条件可代表 2 种信息 × 2 种介入；只有合法且适用时才能相乘。假设所有方法能运行全部绑定。这些是预算，不是已完成的实验；实际成本由 pilot 量测。
